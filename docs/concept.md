# Концепт: площадка агентных закупок (после консультации с ментором, 8 окт ~21:00)

Источник истины для проектирования. Что здесь не записано — не строим.

## 1. Что строим одной фразой

**Marketplace, где агент заказчика покупает у агента исполнителя за деньги с кошелька.
Площадка держит деньги на холде, обе стороны проверяют сделку по контракту, расчёт — только после подтверждения.
Если исполнитель не справился — сделка отменяется, агент идёт к следующему. Человек — крайний случай.**

Для демо — домен «расходники для офиса» (бумага A4, вода, канцелярия).
Архитектура доменно-нейтральна: домен задаётся **типом контракта**, магазины подключаются к **агенту-исполнителю**
через **коннектор**. Новый домен = новый тип контракта; новый магазин = онбординг, без изменения ядра.

Проблема (из брифа): любая сделка между агентами заканчивается тем, что человек платит картой.
У нас человек пополняет кошелёк один раз, дальше агент тратит сам в пределах политики.

## 2. Три стороны и два агента

| Сторона | Кто | Что делает |
|---|---|---|
| **Заказчик** (buyer) | офис / компания | регистрируется, пополняет кошелёк (Stripe test mode), задаёт политику трат, ставит задачи своему агенту (UI или свой MCP-клиент), смотрит realtime-ленту |
| **Магазин** (store) | внешний бизнес | существует сам по себе: лендинг с товарами, описаниями, картинками. Для подключения к площадке делает **минимум**: принимает заказ, шлёт один webhook «заказ зарегистрирован», принимает отмену |
| **Площадка** (platform) | мы | реестр исполнителей (discovery), кошельки и леджер, политика лимитов, state machine сделки, контракты, лог событий, споры как крайний случай |

Поверх этого — **два разных агента**. Это разные модули с разными ролями, своими контрактами с площадкой и своими тестами. Общего у них — только LLM-клиент и шина событий. Не смешивать.

| | Агент-заказчик (`buyer-agent`) | Агент-исполнитель (`provider-agent`) |
|---|---|---|
| За кого | за пользователя площадки | за подключённый магазин (один экземпляр на магазин) |
| Пайплайн | простой и линейный: нужно → кто может → сопоставимы ли условия → принять / отказаться / конфликт | реактивный: запрос оферты → оферта по своим правилам → заказ в магазин → ждать webhook → проверить → отдать Proof или отозвать оферту |
| Инструменты | найти исполнителей, запросить оферты, оценить, принять, отказаться, открыть спор | прочитать каталог, составить оферту, разместить заказ, отменить заказ, отозвать оферту |
| Свои настройки | политика трат, предпочтения, дедлайн, память о ненадёжных исполнителях | привязанный магазин, минимальный заказ, наценка, буфер по срокам |
| Свои валидаторы | оферта ⊆ запрос; proof ⊆ оферта | подтверждение магазина ⊆ размещённый заказ |
| Контракт с площадкой | `BuyerAgentPort`: `runTask(taskId)`; события `TASK_*` | `ProviderAgentPort`: `quote(req)`, `fulfil(dealId)`, `cancel(dealId)`; входящие webhook магазина |
| Тесты | на фиктивных офертах: выбор, отказ по условиям, переключение после отмены | на фиктивном магазине: оферта по правилам, обработка `confirmed / rejected / timeout`, отзыв оферты |

Ключевой принцип: **агенты предлагают, площадка решает.** LLM никогда не трогает деньги.
Холд, лимиты, идемпотентность, переходы состояний — детерминированный код. Это и есть доказательство трёх критериев жюри.

### 2.1 Структура репозитория

```
apps/
  platform/        — API, леджер, реестр, DealService, события, SSE, Stripe, дашборд (Postgres)
  buyer-agent/     — агент-заказчик: цикл, инструменты, промпты, тесты
  provider-agent/  — агент-исполнитель: цикл, инструменты, коннектор магазина, промпты, тесты
  demo-store/      — отдельный мини-проект «магазин» (SQLite, лендинг, order API, webhook, мини-дашборд)
  web/             — React (Vite): лендинг-питч, дашборд заказчика, портал исполнителя, админка; в проде отдаётся платформой как статика
packages/
  contracts/       — ContractType'ы (office-supplies.v1), схемы Req/Quote/Proof, схема webhook магазина
  shared/          — типы событий, LLM-клиент, утилиты
```

Агенты — отдельные процессы (или воркеры), общаются с платформой по HTTP + событиям. Для хакатона допустимо поднимать всё одним `docker compose up`.

## 3. Сущности

```
User ──1:1── Wallet ──1:N── LedgerEntry
 │             └── SpendingPolicy
 ├──1:N── Task ──1:N── Deal ──0:1── Dispute
 │                       └── N:1 ── Provider ──1:1── StoreConnection (url каталога, order API, webhook secret)
 │                                     ├── Capability[] (contractType + категории)
 │                                     ├── CatalogItem[] (снимок каталога магазина)
 │                                     └── Wallet
 └── Event (append-only, realtime + аудит)

ContractType — код, не таблица: схемы запроса / оферты / доказательства + правила валидации.
```

### 3.1 Деньги

- **User** — `id, email, role (buyer|provider|admin), deliveryAddress, preferences`. Админ — отдельная учётка (N5); владелец магазина — `provider`, видит портал исполнителя.
- **Wallet** — `id, ownerType (user|provider|platform), ownerId, currency`. Валюта одна — USD; комиссии площадки нет, место под неё — отдельная строка леджера в будущем (B5). Материализованные `balance`, `held`; истина — леджер.
- **LedgerEntry** — append-only: `id, walletId, type, amount (minor units, signed), dealId?, idempotencyKey UNIQUE, createdAt`.
  Типы: `DEPOSIT, HOLD, HOLD_RELEASE, CAPTURE_OUT, CAPTURE_IN, REFUND`.
- `available = balance − held`. Все операции — одна транзакция с `SELECT … FOR UPDATE` по кошельку, `CHECK (available ≥ 0)`.
- **Идемпотентность**: ключи детерминированы — `hold:{dealId}`, `release:{dealId}`, `capture:{dealId}`, `deposit:stripe:{eventId}`.
  Повтор с тем же ключом возвращает существующую запись. Ретрай агента, дубль webhook, двойной HTTP — одно списание.
- **SpendingPolicy** покупателя: `maxPerDeal, maxPerDay, totalBudget, allowedCategories[]`. Проверяется в момент холда, в той же транзакции.
  Нарушение → `Deal.REJECTED_BY_POLICY` с кодом причины.
- **Что реально**: `DEPOSIT` через Stripe Checkout test mode + webhook — реальная sandbox-транзакция.
  Перевод исполнителю — внутренний леджер; выплата магазину наружу — **`SIMULATED`**.

### 3.2 Контракт (точка расширения №1)

```ts
interface ContractType<Req, Quote, Proof> {
  id: 'office-supplies.v1';
  requestSchema: ZodSchema<Req>;   // что хочет покупатель
  quoteSchema:   ZodSchema<Quote>; // что обещает исполнитель
  proofSchema:   ZodSchema<Proof>; // чем подтверждает исполнение
  validateQuote(req, quote): Violation[];   // у заказчика, до холда
  validateProof(quote, proof): Violation[]; // у заказчика, до расчёта
}
```

`office-supplies.v1` — задача **мультипозиционная**, но исполнитель один на весь заказ и холд один (решение B3):
- `Req`: `{ items: [{ itemQuery, quantity, unit, category }], categories[], budget: { max, source: 'user' | 'estimated' }, deadline, deliveryAddress }`
- `Quote`: `{ lines: [{ itemIndex, sku, title, unitPrice, quantity, lineTotal }], total, deliveryEta, validUntil }`
- `Proof`: `{ storeOrderId, invoiceNumber, lines: [{ sku, confirmedQuantity }], confirmedTotal, deliveryEta, trackingNumber? }`
- `validateQuote`: на каждый `items[i]` ровно одна `line` с `quantity == items[i].quantity`; `total ≤ budget.max` (нарушение — ошибка при `source: user`, предупреждение при `source: estimated`); `deliveryEta ≤ deadline` (сравнение по **дате**, не по времени); `validUntil > now`.
- `validateProof`: на каждую `quote.line` — `confirmedQuantity ≥ line.quantity`; `confirmedTotal ≤ quote.total`; `deliveryEta ≤ quote.deliveryEta` по дате; `invoiceNumber` непустой.
- Деньги везде — целые minor units (центы). LLM отдаёт десятичные — конвертация на границе, в схемах `Quote/Proof` только целые.
- Нет хотя бы одной позиции → исполнитель оферту **не даёт** (весь заказ или ничего, B4). Discovery: исполнители, чьи `capabilities` покрывают **все** `categories` задачи.
- **Категории — фиксированный enum контракта**: `paper | writing | water | office`. Заказчик относит каждую позицию к категории из этого списка, исполнитель при онбординге раскладывает каталог по нему же. Иначе discovery по свободным тегам не сойдётся.

Сверх правил — LLM-сверка «это та бумага?» по каждой строке (`itemQuery` ↔ `title` + описание). Результат — score для выбора агентом, **не** условие расчёта.
Второй тип контракта не делаем; показываем слайдом: «оборудование — больше полей, те же четыре функции».

### 3.3 Магазин и его подключение (точка расширения №2)

Магазин — внешняя система. Требования к нему минимальны, это и есть предложение для онбординга:

```
GET  {apiUrl}/catalog             — весь каталог JSON: [{ sku, title, description, unit, price, category? }] (агент читает при онбординге и по кнопке «пересинхронизировать»)
GET  {apiUrl}/products/{sku}      — живая цена и остаток (агент «ходит в магазин» перед офертой)
POST {orderUrl}                   — { items:[{sku, qty}], deliveryAddress, buyerRef }  → { storeOrderId, status:'pending' }
POST {orderUrl}/{storeOrderId}/cancel
→ магазин шлёт один webhook своему агенту-исполнителю:  POST {providerAgentUrl}/hooks/store
     { storeOrderId, status:'confirmed'|'rejected', invoiceNumber, confirmedQuantity, confirmedTotal, deliveryEta, trackingNumber? }
     подпись HMAC по секрету из онбординга
```

**Онбординг магазина** (портал исполнителя): название → базовый URL API магазина → генерируем webhook URL + секрет.
Агент-исполнитель читает `GET /catalog` (JSON, парсить HTML не нужно), LLM только **раскладывает товары по категориям контракта** и предлагает `capabilities`,
владелец подтверждает. Готово — магазин в реестре, у него кошелёк. Лендинг магазина с картинками — для людей и для видео, агент его не читает.

**Демо-магазин — отдельный мини-проект `apps/demo-store`.** Он ничего не знает про площадку, кроме контракта выше. Внутри:
- своя **SQLite** (товары, остатки, заказы);
- лендинг с товарами (бумага, вода, канцелярия), описания, картинки;
- order API: заказ резервирует остаток; остатка нет → webhook `rejected` с причиной `out_of_stock`;
- **мини-дашборд магазина**: заказы, статусы, остатки, кнопки «подтвердить / отклонить / списать остаток». На видео в него заглядываем: «вот заказ появился, вот остаток кончился, магазин отклонил»;
- webhook подписывается HMAC и шлётся с ретраями.

Запускаем **четыре экземпляра с разными seed-данными** — один код, четыре «разных магазина» в реестре, у каждого свой агент-исполнитель с своими настройками:

| # | Магазин | Ассортимент | Роль в демо |
|---|---|---|---|
| 1 | **AquaDoručení** | только вода 19 л, стаканы | безотказный: всегда есть, всегда подтверждает. Вопрос только в расписании: доставка вт/чт, оферта даёт ближайший слот. Если дедлайн раньше слота — заказчик отклоняет по условиям |
| 2 | **Papírna Holešovice** | бумага, конверты, ручки | **высокий рейтинг, склад с отставанием**: `GET /products` отдаёт остаток из ночного снимка склада (5), а резерв при заказе идёт по живому складу (2 после офлайн-продажи). Заказчик идёт к нему первым, оферта проходит, заказ получает `out_of_stock` → исполнитель отзывает оферту → переключение. Флаг `inventoryLag: true` в seed, в дашборде магазина видны оба числа и кнопка «продать офлайн» |
| 3 | **Kancelář Plus** | широкий ассортимент, средние цены, всё в наличии | «спасает» после отзыва №2 — на нём закрывается happy path |
| 4 | **Levný Papír** | самый дешёвый, доставка 7 дней | отсеивается ещё на оферте: срок позже дедлайна. Показывает, что дешевле ≠ подходит |

Ассортименты частично пересекаются (A4 есть у 2, 3, 4; вода — только у 1; ручки — у 2 и 3), чтобы заказчику было из чего выбирать и чтобы discovery по категории давал разные множества.

Через демо-магазин тестируем сам **онбординг** (подключение по URL) и обработку webhook. Честно помечаем: магазины демонстрационные, но интегрированы по тому же контракту, что ждёт реальный.

### 3.3.1 Рейтинг исполнителя

`Provider.rating` — число 0–5, seed при онбординге (в демо: №2 = 4.9, №3 = 4.2, №4 = 3.8, №1 = 4.7).
Автоматически корректируется площадкой: `SETTLED` → +0.05 (до 5), `OFFER_WITHDRAWN` → −0.3, `DEAL_CANCELLED` по вине исполнителя → −0.5.
Отзывы пользователя — P2. Рейтинг виден в реестре и в ленте («рейтинг Papírna снизился до 4.6 после отзыва оферты»).

### 3.4 Агент-исполнитель

Запускается площадкой, один на магазин, со своими инструментами:

| Инструмент | Что делает |
|---|---|
| `read_catalog()` | `GET /catalog` → снимок `CatalogItem[]` с категориями контракта (при онбординге и по кнопке «пересинхронизировать») |
| `make_quote(req)` | LLM подбирает товар под каждый `itemQuery` по снимку каталога, затем **ходит в живой магазин** `GET {storeUrl}/products/{sku}` за актуальной ценой и остатком (B15). Применяет правила магазина (наличие на весь заказ, мин. заказ, наценка). **Срок** считает сам: расписание/lead time магазина + буфер → абсолютный `deliveryEta` (B7). → `Quote` или отказ с причиной |
| `place_order(deal)` | `POST {orderUrl}` → `storeOrderId`; сделка ждёт webhook |
| `on_store_webhook(payload)` | свой валидатор: подтверждение магазина соответствует размещённому заказу (sku, qty, сумма) → собирает `Proof` и отдаёт площадке |
| `withdraw_offer(deal, reason)` | магазин прислал `rejected` (нет остатка, не доставим) или не ответил → исполнитель сам отзывает оферту у площадки с причиной. Это его ответственность, не заказчика |
| `cancel_order(deal)` | `POST …/cancel` при отмене сделки со стороны заказчика или площадки |

Правила исполнителя — часть его конфигурации при онбординге (простой JSON: `minOrderTotal, markupPct, etaBufferDays`).

### 3.5 Задача и сделка

**Task**: `{ userId, contractTypeId, request: Req (items[] — несколько товаров, один исполнитель, один холд), status, createdVia: ui|mcp, excludedProviderIds[] }`.
Статусы: `OPEN → SOURCING → DECIDING → ORDERED → DONE | FAILED`.

**Deal** — пара «задача × исполнитель». Все переходы — в `DealService`:

```
QUOTED ──accept(policy+HOLD)──▶ HELD ──place_order──▶ ORDER_PLACED ──store webhook──▶ PROOF_RECEIVED ──validate ok──▶ SETTLED (CAPTURE)
  │                               │                        │                                │
  │ policy fail                   │ store error / timeout   │ store rejected / timeout       │ validate fail
  ▼                               ▼                        ▼                                ▼
REJECTED_BY_POLICY            CANCELLED ◀──────────────────┴────────────────────────────────┘
                              (HOLD_RELEASE, cancel_order → магазину, задача обратно в DECIDING)
```

- В `CANCELLED` сделку приводят две стороны по-разному:
  - **исполнитель отзывает оферту** (`withdraw_offer`): магазин ответил `rejected` или молчит. Площадка снимает холд, пишет событие `OFFER_WITHDRAWN {providerId, reason}`;
  - **заказчик отказывается** (`validateProof` не прошёл): площадка снимает холд и через исполнителя шлёт магазину `cancel_order`.
- Агент-заказчик видит `OFFER_WITHDRAWN` / `DEAL_CANCELLED`, помечает исполнителя как ненадёжного для этой задачи (а при повторах — в предпочтениях пользователя) и берёт следующую оферту по рангу. Оферты исчерпаны → `Task.FAILED`, уведомление пользователю.
  **Человек не нужен**: деньги вернулись холдом, магазин уведомлён.
- `SETTLED` ставится, когда `validateProof` прошёл. Доставку не ждём — сценарий автономен от начала до конца.
- Таймауты: ответ магазина на заказ — 60 с в демо (конфигурируемо). Нет webhook → `CANCELLED`.

**Dispute — только крайний случай**, не в основном сценарии:
- после `SETTLED` пользователь нажимает «проблема с заказом» (товар не приехал);
- или `cancel_order` магазину не доставился, а деньги уже на холде/списаны.
Статус `DISPUTED` открывается вручную, деньги замораживаются, админ решает: `settle / refund / partial`. Один экран, три кнопки. P1.

### 3.6 Агент-заказчик

| Инструмент | Что делает | Кто решает |
|---|---|---|
| `parse_task(text)` | свободный текст → `Req`: позиции, количества, категории из enum, дедлайн абсолютной датой, адрес из профиля; что предположил — в лог. В UI — форма с кнопкой «заполнить из текста» (N1) | агент |
| `estimate_budget(req)` | **если пользователь не назвал бюджет** — агент оценивает сам: LLM даёт ожидаемую рыночную цену позиций, агент берёт оценку × 1.3 и режет сверху политикой (`maxPerDeal`, `available`). Пишет в `Req.budget {max, source:'estimated'}` и в лог: «ожидаю 45–60 $, потолок 60 $». Если даже оценка выше `maxPerDeal` — задача завершается `FAILED: over_policy` до запроса оферт. **Оценённый бюджет — мягкий**: оферта выше него, но в пределах политики, не отбрасывается, а штрафуется в score и помечается в логе «дороже ожидания»; оферта выше оценки ×2 отбрасывается как ценовая аномалия. Жёсткая граница всегда одна — политика. Бюджет от пользователя (`source: user`) — жёсткий | агент |
| `find_providers(contractTypeId, categories[])` | реестр → исполнители, покрывающие все категории | платформа |
| `request_quotes(taskId, providerIds[])` | параллельно `make_quote` у агентов-исполнителей → `Deal.QUOTED` на каждого | платформа |
| `evaluate_quotes(taskId)` | `validateQuote` + предпочтения пользователя + LLM-сверка товара → ранжированный список | смесь |
| `accept_quote(dealId)` | политика + холд → дальше сделка едет сама (`place_order` → webhook → `validateProof` → `CAPTURE`) | платформа |
| `fail_task(taskId, reason)` | подходящих оферт нет | агент |

Агент выбирает, у кого покупать, и к кому идти после отмены. Обойти политику, валидацию или заплатить дважды он не может.
Предпочтения пользователя (`preferredProviders[], preferredBrands[]`, свободный текст) подмешиваются в промпт `evaluate_quotes`.

**Правило ранжирования** (чтобы демо было предсказуемым, а не «как LLM решит»):
1. оферты с нарушениями `validateQuote` — вне списка, с причиной в ленте;
2. оферты от исполнителей, помеченных ненадёжными в рамках этой задачи, — вне списка;
3. остальные сортируются по `score = rating × 0.5 + соответствие товару (LLM, 0–1) × 0.3 + ценовое преимущество (0–1) × 0.2`, предпочтение пользователя добавляет +0.5.
Формула — в коде, LLM даёт только «соответствие товару». В ленте показываем таблицу score по каждой оферте.

### 3.7 MCP-инструменты пользователя

MCP-сервер площадки (`@modelcontextprotocol/sdk`, HTTP): `create_task, get_task, wallet_balance, list_deals`, авторизация по API-ключу.
Пользователь из своего Claude говорит «закажи воду» — та же задача, что из UI.

### 3.8 Наблюдаемость: один журнал на домен и на агентов

**Решение:** не два журнала (события домена отдельно, логи агентов отдельно), а **одна таблица `events`** с полем `kind`. Админка и лента читают её одним запросом, SSE — один поток.

```
Event {
  id            bigserial            -- порядок, курсор для SSE
  ts
  kind          'domain' | 'agent'   -- что случилось с сущностью / что делает агент
  actor         'platform' | 'user:{id}' | 'buyer-agent' | 'provider-agent:{providerId}' | 'store:{providerId}' | 'stripe'
  runId?        -- один прогон агента (одна задача у заказчика, одна сделка у исполнителя)
  taskId? dealId? providerId? userId?
  type          -- domain: TASK_CREATED, DEAL_QUOTED, HOLD_PLACED, OFFER_WITHDRAWN, DEAL_SETTLED, …
                -- agent:  STEP_STARTED, TOOL_CALL, TOOL_RESULT, WAITING, DECISION, ASSUMPTION, STEP_FAILED
  payload       jsonb   -- для agent: { step, tool, args, result(summary), waitingFor, until, reasoning }
  correlationId -- x-request-id, сквозной через все сервисы
}
```

Агент пишет не «текст в консоль», а **структурированные шаги** через `K3/K5 event(...)`: начал шаг «запрос оферт», вызвал `find_providers` с такими аргументами, получил 3 исполнителя, принял решение «№2, потому что…», **ждёт** webhook магазина №2 до 22:14:30. Админка показывает это как таймлайн по задаче: колонка заказчика, колонка платформы, по колонке на исполнителя, по колонке на магазин — ровно как sequence-диаграмма C11/C19, только живая. Состояние «ждёт» показывается с обратным отсчётом.

Где это видно:
- **админка** — все задачи, все агенты, фильтр по `actor / kind / type`, таймлайн по задаче, «что сейчас делает каждый агент» (последнее `agent`-событие на `runId`);
- **дашборд заказчика** — то же по своим задачам, без внутренностей исполнителей (видит `OFFER_WITHDRAWN`, не видит, что исполнитель ходил в `GET /products`);
- **портал исполнителя** — свой агент: оферты, походы в магазин, webhook'и, отзывы оферт;
- **дашборд магазина** — свои заказы, из своей SQLite; к `events` платформы доступа нет.

Это дёшево: одна таблица, один SSE-эндпоинт с фильтром по роли, один React-компонент таймлайна. И это то, что жюри смотрит на видео.

### 3.9 События и realtime

Таблица из 3.8, append-only, пишут все сервисы и оба агента. Дашборд подписан по SSE. Уведомления — фильтр событий (`REJECTED_BY_POLICY, DEAL_CANCELLED, TASK_DONE, TASK_FAILED`) в колокольчике.
В ленте видно обе стороны: «исполнитель Papírna: подобрал SKU A4-80, оферта 42 $» и «заказчик: оферта принята, холд 42 $».

## 4. Сквозной сценарий (должен работать до всего остального)

1. Пользователь регистрируется → кошелёк, политика по умолчанию (`maxPerDeal 50, maxPerDay 100, total 100`).
2. Пополняет 100 $ через Stripe Checkout (test card) → webhook → `DEPOSIT`. **Реальная sandbox-транзакция.**
3. Ставит задачу: «5 больших пачек бумаги A4, не дороже 60 $, до пятницы» (UI или MCP).
4. Агент-заказчик находит по категории `paper` три магазина (№2, №3, №4; вода №1 не попадает) → три агента-исполнителя составляют оферты из своих каталогов → №4 опаздывает к дедлайну (вне списка), №2 первый по рейтингу, №3 второй.
5. `accept` №2 → политика ок → `HOLD` → исполнитель размещает заказ → магазин №2 отвечает webhook `rejected: out_of_stock` → исполнитель отзывает оферту → холд снят, рейтинг №2 −0.3 → заказчик берёт №3 → `HOLD 42 $` → заказ → webhook «confirmed, счёт №…, 5 шт, трек» → Proof → `validateProof` ок → `CAPTURE` → `SETTLED`.
6. Лента показывает каждый шаг с обеих сторон; баланс покупателя 58 $, кошелёк магазина №3 +42 $. В дашборде магазина №3 — новый заказ, в дашборде №2 — отклонённый.

Демо критериев жюри поверх сценария:
- **(а) Без кнопок**: шаги 3→6 без человека.
- **(б) Лимит**: задача «20 пачек, 160 $» → `REJECTED_BY_POLICY: maxPerDeal`, баланс не изменился.
- **(в) Нет двойного списания**: повтор `accept` / повтор Stripe webhook / повтор webhook магазина → леджер не изменился, в ленте `IDEMPOTENT_REPLAY`. Плюс тест.
- **Failure cases (для «5» по критерию 1)**: переключение после `out_of_stock` уже в основном сценарии (шаг 5). Дополнительно на видео или в тестах: магазин подтвердил заказ с другими условиями (6 шт по другой цене, срок позже) → `validateProof` fail → заказчик отменяет → магазину уходит `cancel` → переключение. Полный список — раздел 8.

## 5. Сложные места и как их решаем

| Место | Риск | Решение |
|---|---|---|
| Денежная консистентность | гонки, двойной холд, отрицательный available | один `LedgerService`, транзакция с `FOR UPDATE`, `UNIQUE(idempotencyKey)`, `CHECK`, тест с параллельными вызовами |
| LLM в контуре денег | агент «уговорит» себя потратить больше | у агентов нет денежного инструмента; `accept_quote` всегда проходит политику в коде |
| Асинхронный магазин | сделка зависла в `ORDER_PLACED` | таймаут → `CANCELLED` + `cancel_order`; webhook идемпотентен по `storeOrderId` |
| Отмена после подтверждения | магазин уже зарезервировал, а мы отменили | это нормальная бизнес-ветка: шлём cancel, магазин снимает резерв. Не дошло — единственный путь в `DISPUTED` |
| Недетерминизм демо | агент на видео выбирает не то | seed каталогов фиксирован, промпты жёсткие, `temperature 0`; видео пишем с заранее прогнанного сценария |
| Категории каталога | LLM разложит товары не по тем категориям | категории — фиксированный список в контракте (`paper, writing, water, office`); LLM выбирает из него, владелец видит и подтверждает при онбординге |
| Валидация «та ли бумага» | LLM ошибётся | LLM даёт score, блокируют только правила контракта; пишем в limitations |
| Stripe локально | webhook | `stripe listen --forward-to`; fallback — кнопка `SIMULATED deposit`, помеченная |
| Discovery | звучит больше, чем есть | честно: реестр + фильтр по контракту и категории, LLM ранжирует оферты |
| Объём работы | два агента + магазин + площадка за ночь | агенты раздельные, но каждый — маленький: один файл цикла + инструменты + промпт; общий LLM-клиент в `packages/shared`; магазин — один сервис в четырёх экземплярах; UI — минимальный |
| Связность агентов | соблазн срезать и вызывать одного агента из другого | агенты не знают друг о друге: общаются только через площадку (`Deal`, события). Тесты каждого — на фиктивной площадке |

## 7. Честные ограничения (в README)

- Реальная транзакция — пополнение через Stripe test mode. Перевод магазину — внутренний леджер, `SIMULATED`.
- OTP-код не отправляется по email, а показывается в интерфейсе (`SIMULATED email`). MCP защищён API-ключом, а не OAuth 2.1.
- Магазины в демо — наш мини-сервис в трёх экземплярах, подключённый по тому же контракту, что ждёт реальный магазин.
- Discovery — реестр с фильтром, не децентрализованный протокол.
- Споры — ручной крайний случай; в автономном сценарии человек не участвует.
- Один тип контракта. Расширяемость показана интерфейсом, а не вторым доменом.
- Заказ из нескольких позиций исполняет один магазин; разбиения заказа между магазинами нет.

## 9. Слепые зоны и предлагаемые решения

Каждый пункт — решение по умолчанию. Если не оспорено, так и строим.

| # | Вопрос | Предлагаю |
|---|---|---|
| B1 | **Как платформа вызывает агентов?** Процессы, HTTP, очередь? | **Решено.** Агенты — отдельные HTTP-сервисы на своих портах. Платформа вызывает исполнителя: `POST /quote` (синхронно, ответ — оферта или отказ), `POST /fulfil` и `POST /cancel` (отвечают `202`, результат приходит через K5). Заказчика: `POST /run {taskId, reason}` — отвечает `202` и работает в фоне, результат через K3. Агенты вызывают платформу через её API. Очередей нет. **Таймаут ожидания магазина держит исполнитель** (он отзывает оферту); у платформы страховочный таймер ×2 на случай смерти агента — P1 |
| B2 | **Один процесс исполнителя на все магазины или четыре?** | **Решено: четыре.** Каждый агент-исполнитель — свой процесс на своём порту, привязан к одному магазину через env (`STORE_URL, PROVIDER_ID, WEBHOOK_SECRET`). Шум в compose принимаем ради предсказуемости и изоляции при тестах. Итого сервисов: Postgres, платформа, заказчик, 4 исполнителя, 4 магазина = 11, плюс Stripe CLI — нужно **два блока портов** |
| B3 | **Одна задача = один товар?** | **Решено: нет.** Задача — несколько позиций, но **один исполнитель на весь заказ и один холд**. Нет хотя бы одной позиции → оферты нет. Разбивать заказ между магазинами не умеем, и это честно пишем в limitations |
| B4 | **Частичное исполнение** (есть 3 из 5) | **Решено: не принимаем.** Правило магазина: нет полного остатка → `rejected`. Правило заказчика: `confirmedQuantity ≥ quantity`. Partial — только через спор, P1 |
| B5 | **Валюта и комиссия площадки** | **Решено.** Только USD. Комиссии нет — вся сумма уходит исполнителю. Комиссия — опциональная будущая строка леджера, в коде место оставляем, не реализуем |
| B6 | **Что считает `maxPerDay`** — холды или списания? | **Решено.** Холды + списания за день, `HOLD_RELEASE` вычитается. Иначе агент сможет «забронировать» сверх лимита |
| B7 | **Время в демо** | **Решено.** Инжектируемые часы (`Clock`), абсолютные даты, таймаут webhook 60 с в демо / 100 мс в тестах. Заказчик превращает «до пятницы» в абсолютный дедлайн при разборе задачи; **исполнитель** отвечает за `deliveryEta` — считает из расписания и lead time магазина |
| B8 | **Аутентификация** | **Решено (обновлено).** Пользователи: настоящие сессии (cookie, таблица `Session`) и **вход по OTP-коду на email**. Email-отправки нет — код показывается в UI/логе с пометкой `SIMULATED email`; отправку через реальный провайдер подключим, если останется время. Одна сессия держит **несколько учёток** (`identities[]`, `activeIdentity`): войдя как заказчик, можно добавить админа и исполнителя и переключаться без повторного входа — для демо и для жизни. Роли: `buyer / provider / admin`, доступ к разделам по роли. Магазин → агент: HMAC с timestamp + nonce (как у Stripe). Платформа ↔ агенты: короткоживущий JWT (HS256, общий секрет, `iss/aud/exp`). MCP: API-ключ пользователя в заголовке — стандарт MCP предполагает OAuth 2.1, но для хакатона это несоразмерно; честно пишем в limitations |
| B9 | **Память о ненадёжных исполнителях** | **Решено.** В рамках задачи — `Task.excludedProviderIds[]`. Долгосрочно — рейтинг (3.3.1) |
| B10 | **LLM в тестах** | **Решено.** У каждого агента интерфейс `Llm`; в тестах `FakeLlm` с детерминированными ответами (сопоставление товара по подстроке). Реальная модель — только в e2e и демо, `temperature 0`. Ключ Anthropic есть, кладётся в `.env` на старте кода |
| B11 | **Что если API модели ляжет на демо** | **Решено.** Записанное видео — главный артефакт; живой питч — с флагом `LLM=fake`, честно говорим |
| B12 | **Stripe-аккаунт и ключи** | **Решено.** Sandbox-аккаунт у пользователя есть или будет заведён. Для демо достаточно: кнопка «Пополнить» → Stripe Checkout → возврат в приложение → баланс вырос. Webhook — через `stripe listen`. Кнопка `SIMULATED deposit` остаётся как fallback и для тестов |
| B13 | **Магазин не знает про `dealId`** | **Решено.** Связь `storeOrderId ↔ dealId` хранит исполнитель. `buyerRef` в заказе — непрозрачный идентификатор |
| B14 | **Порядок событий и SSE** | **Решено.** `Event.id` — монотонный `bigserial`, клиент хранит `lastId`, при reconnect шлёт `since` |
| B15 | **Оферта по снимку или по живому магазину?** | **Решено: по живому.** Снимок каталога нужен только для сопоставления «что за товар». Перед офертой исполнитель запрашивает `GET /products/{sku}` — актуальная цена и остаток. На видео это выглядит как «агент сходил в магазин». Расхождение между офертой и подтверждением всё равно ловит `validateProof` (C21) |
| B16 | **Кошелёк исполнителя** | **Решено.** Создаётся при онбординге, баланс виден в портале исполнителя — **показываем на видео** один кадр с выросшим балансом. Вывод наружу — `SIMULATED` |
| B17 | **Фронт** | **Решено: React (Vite), `apps/web`.** Зоны: лендинг-питч, заказчик, портал исполнителя, админка. Дашборд магазина — внутри `demo-store`, намеренно чужой по стилю: «это не мы, это магазин» |
| N1 | **Разбор свободного текста в `Req`** | **Решено: оба пути.** Форма с полями + кнопка «заполнить из текста» (LLM заказчика). Недостающее — из профиля и политики, предположения — в ленту |
| N2 | **Адрес доставки** | **Решено.** В профиле пользователя, уходит магазину в заказе |
| N3 | **Модель** | **Решено.** Claude Sonnet 5.5 для обоих агентов, `temperature 0`. Opus — только если Sonnet ошибается в сопоставлении товаров |
| N4 | **Возврат из Stripe Checkout** | **Решено.** `success_url` ведёт на страницу, которая ждёт событие `DEPOSIT` по SSE и показывает «зачисляется…». Баланс не читаем сразу |
| N5 | **Админ** | **Решено.** Отдельная учётка с ролью `admin`, своя админка (споры, реестр, леджер) |
| N6 | **Лендинг** | **Решено.** Лендинг площадки — место для питча: структура как у питч-дека (проблема → решение → как работает → что реально / SIMULATED). Делается в конце ночи вместе со слайдами, **P1** |
| N7 | **Портал исполнителя в видео** | **Решено: нужен.** Онбординг магазина по URL — второй «вау-момент» после переключения. Переходит в **P0** |

### Про авторизацию агентов: есть ли «готовый протокол»

Короткий честный ответ: общепринятого стандарта «агент авторизуется у агента» сейчас нет.
- **MCP** для удалённых серверов предписывает OAuth 2.1 — это целый authorization server, за ночь не стоит. API-ключ в заголовке — то, что реально делают сейчас большинство MCP-серверов и клиентов; оставляем и честно пишем.
- **A2A (Agent2Agent)** описывает «карточку агента» (`/.well-known/agent.json`: кто я, что умею, как со мной авторизоваться) поверх обычных схем — OAuth/API key/JWT. Сам протокол нам не нужен, но **карточку агента отдать дёшево** (20 минут) и это красиво ложится на ось discovery из брифа: реестр платформы можно показать как «мы читаем карточки агентов». P1, опционально.
- Между нашими сервисами — **JWT HS256 с `iss/aud/exp`** по общему секрету. Это обычная service-to-service практика, лучше статического ключа и укладывается в полчаса.
- Магазин → агент — **HMAC + timestamp + nonce**, как у Stripe и GitHub. Это и есть индустриальный стандарт для webhook'ов.
